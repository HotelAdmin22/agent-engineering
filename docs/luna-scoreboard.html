What has been tried

Green kept, red reverted, grey no measurable effect. The grey ones matter most: they are the ideas that sound right and are not.

exp1-sql-mode-tool-surfacekeep

Changed: sql mode's tool list: 7 tools -> 4 (search_catalog, describe_table, get_join_path, run_sql). Prompt also gained one line about double braces.

End-to-end accuracy 33.3% -> 66.7%. Every answer became scorable (9 -> 15) and placeholder leakage went 7 -> 0, which is the mechanism the hypothesis named. Tokens fell 8% as a side effect of a smaller tool surface.

exp2-dbt-yml-promptrevert

Changed: evals/dbt/prompts/main.md gained a 'Read the schema files first' section

REFUTED, and expensively. Accuracy moved 0.2344 -> 0.224, inside overlapping noise bands (0.219-0.250 vs 0.188-0.250) and therefore not a real change. The non-noise signal was cost: max_turns 5 -> 29, budget failures 4 -> 23, mean input tokens 280k -> 479k, cost $5.79 -> $9.76. The longer prompt bought diligence at a bad exchange rate -- the agent spent its budget inspecting instead of building.

exp3-gateway-catalog-accesskeep

Changed: gateway: engine catalog exempt from the allowlist (information_schema / sqlite_master); refusals name the schema-qualified reference; DuckDB describe() covers every user schema. Prompt reverted to baseline.

CONFIRMED on mechanism, NULL on accuracy -- which is what was predicted in writing before the run. The two target categories collapsed: catalog refusals 168 -> 0 across 7,312 calls, schema qualification 95 -> 11 (-88%), overall failed-call rate 6.5% -> 4.0%. Accuracy moved 0.2344 -> 0.250 (15 -> 16 of 64) with fully overlapping noise bands, and pass^3 is identical at 0.156. Task-level churn confirms it is noise: 5 tasks gained, 4 lost, 16 shared.

exp4-inject-model-specrevert (inject_model_spec = false; code and tests kept, flag-controlled)

Changed: evals/dbt/spec.py: models/**/*.yml condensed (names, descriptions, column names) and appended to the task instruction by the runner. ~800 tokens, median 2.6 KB.

REFUTED. The block costs ~800 tokens to deliver and raised mean input tokens by 147,000 per attempt -- 180x its own size -- because it made the agent do more work, not because it is long. Mean turns 19.3 -> 23.6, attempts hitting the 40-turn cap 2 -> 19, cost +51%, and 28 passes against 31. Naming a mean of 11.1 models and saying each must exist sent the agent off building models the task never asked for. This is exp2's failure mode reproduced through a cheaper delivery mechanism, which means the mechanism was never the problem.

exp5-dbt-test-gaterevert (test_gate = false; code and tests kept)

Changed: runner.test_gate(): after the agent stops, run `dbt test`; on failure hand the failing assertions back for one repair pass. Structural gate, not a prompt line.

NULL, and it costs. pass@1 0.250 -> 0.234, inside overlapping noise (0.219-0.266 vs 0.203-0.266) and pass^3 identical at 0.156, for +16% cost and +19% turns. The gate works mechanically: it fired on every completed attempt and named the right rows -- provider001's assertions flagged the same 2,857 rows an independent gold diff found. It simply does not convert. Over 157 gated attempts, those whose assertions passed clean scored 0.259 and those that failed and were repaired scored 0.222; retail001 passed, was repaired, then failed.

What the evidence says

The bottleneck is not information

Three changes gave the agent more or better information — catalog access, the .yml spec read by the agent, the same spec injected for free. The catalog fix removed real waste (168 refused reads → 0, failed-call rate 6.5% → 4.0%) and moved accuracy by nothing. The two spec changes made it worse by spending turns.

The bottleneck is not awareness of failure

80% of these projects declare column tests — 809 not_null, 280 unique — targeting exactly the measured failure modes. Wiring them in as a gate with a repair pass surfaced the right rows (provider001's assertions named the same 2,857 rows a gold diff found) and still did not convert: repaired attempts passed at 0.222 against 0.259 for attempts whose assertions were already clean.

Where the 20 tasks actually are

In the best run, 10 tasks passed all three attempts and 11 passed one or two. The ceiling from making flaky tasks reliable is 21/64, which is where the target lives. But passing and failing attempts of the same task are operationally indistinguishable — 19.1 vs 20.1 turns, 1.7 vs 2.2 tool errors. The variance is in the model's sampling, not in the harness.

Five tasks can never pass

xero_new001, xero_new002, social_media001, chinook001, tpch002 — verified 0 of 9 attempts each across three runs. Broken gold filenames, gold missing the compared tables, and one task whose starting database ships 1 of the 8 source tables it needs.
