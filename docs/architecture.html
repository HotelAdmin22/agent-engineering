The loop this exists to run

A single question being answered is one box inside step 2. The unit of work here is a sweep, and the unit of progress is a recorded experiment.

  1. 1
    Sweepdocker compose run --rm sweep135 Spider tasks through one agent, in a container that cannot reach the answer key. Resumable; a sweep takes hours.
  2. 2
    Recordruns/<sweep>/<task>/answer.json, evidence.jsonl, audit.jsonl per task. Written DURING the run, so an interrupted task is still diagnosable.
  3. 3
    Verifydeterministic, no modelDid it produce SQL? Did it actually RUN the SQL it submitted? Did that return rows? A model never grades its own work.
  4. 4
    Scoreevals/spider/evaluation_suite/evaluate.pySpider's own scorer, on the HOST, against gold the container never saw. Never a home-grown scorer -- a lenient one invents improvements.
  5. 5
    Triageevals/run_triage.pyA read-only agent reads failure signatures across every run and proposes fixes. It has no write tool and cannot propose changes to its own judges.
  6. 6
    Experimentexperiments/results.jsonlOne variable changed, re-measured, written down whether it helped or not. `inconclusive` is a real and common outcome.

Structural guarantees

The agent runs in a container

docker compose run --rm sweep

The image pins Python and every dependency from uv.lock, and carries neither the answer key nor the credentials. A sweep is reproducible from source rather than from one laptop's state.

Read-only database handle

sqlite3 opened with file:...?mode=ro

A write is rejected by SQLite itself, whatever SQL arrives. A keyword check would only be a guess about what the model might try.

No file access from SQL

enable_external_access=false + lock_configuration=true

read_only=True stops writes and says nothing about reads. DuckDB will run read_json_auto('evals/gold/questions.jsonl'), and the table allowlist never fires because a table function is not a table. Verified: 7 of 9 file-read attempts reached the gold answers before this was added.

One database per task

ATTACH and DETACH denied by a connection authorizer

mode=ro stops writes but still permits ATTACH, which reaches other files on disk -- including the gold answers. Verified: ATTACH succeeded before the authorizer was added.

No file, shell, or network tool

The tool list contains exactly one entry

There is no path from query_database to the grading key, so no prompt wording and no model decision can reach it.

The verifier cannot fix anything

It is handed the same single read-only tool

Its only possible output is a report. An auditor that can edit the work is not an auditor.

The verifier cannot close its own findings

findings.check_landed() re-runs the evidence query

Whether feedback landed is arithmetic on a row count, not a model's opinion of its own work.

Modules

Capability surfacegateway/

The only module that may import duckdb or execute SQL. The model proposes, this decides. parse -> authorize -> lint -> rewrite -> cost -> execute.

src/agent/gateway/backends.py281 lines

Engine-specific pieces of the gateway. The policy does not live here.

Parse, authorize, lint, cost and the LIMIT rewrite are all dialect-parameterised sqlglot, so they work unchanged on either engine. What genuinely differs is four things, and that is all a backend is:

1. how to open a connection that CANNOT write and CANNOT read other files 2. how to bound a statement in time 3. how to read the schema 4. which exception means "the engine interrupted this"

src/agent/gateway/gateway.py287 lines

The only module that may open a database or execute SQL.

The model proposes SQL. This decides. Those are different jobs, and keeping them in different modules is what makes the boundary real rather than a rule written in a prompt -- the agent is never handed a connection object, so no wording and no model decision can reach the warehouse another way.

The pipeline, in order:

Evidenceevidence/

Immutable records of everything that ran. Every number in a report resolves to an id here, or it does not get published.

src/agent/evidence/redact.py128 lines

Mask likely personal data before it is written to disk.

The evidence store keeps raw result rows so a number can be traced back to the query that produced it. On a synthetic warehouse that is harmless. On a real one it means customer records in a JSONL file that nothing treats as sensitive, sitting in `runs/` next to the transcripts.

Two independent rules, because either alone misses the obvious case:

src/agent/evidence/store.py190 lines

Immutable evidence records. Every number the system reports comes from here.

The rule this enforces: a model may propose SQL and may describe what it means, but it may never be the source of a digit. Each executed query and each deterministic computation writes a record, gets an id (`e1`, `e2`, ...), and the report refers to that id rather than restating the value.

Records are append-only. There is no update method, deliberately -- an evidence store that can be edited after the fact proves nothing about what was run.

Orientationcatalog/

Cards for tables and metrics, so the agent's first move is a search rather than a guessed table name.

src/agent/catalog/catalog.py189 lines

Cards for every table and metric, and keyword search over them.

Why a catalog at all: without one the agent's first move is `SELECT *` against a guessed table name, and its second is a different guess. The catalog turns orientation into one cheap call instead of several refused queries.

Why keyword search rather than embeddings: with three tables and six metrics, a vector index would be machinery with no blocked step behind it. The scoring below is deliberately unclever, and should be replaced when a question starts failing to find the table it needs -- not before.

Deterministic mathtools/

Deltas, contribution, and the mix-versus-rate split. Takes evidence ids, never literal numbers -- the model chooses what to compute, not the answer.

src/agent/tools/math.py200 lines

Deterministic arithmetic. The model chooses what to compute, never what the answer is.

Every function here takes evidence ids and column names -- never literal numbers. That is the whole design. A tool signature like `compute_delta(current=52270, previous=22320)` would let the model type a digit into an argument, and a mistyped digit is indistinguishable from a correct one once it is inside a result. Taking ids means the inputs are whatever the warehouse actually returned.

Each function writes its own computation evidence, so a report can cite `{{e9.delta_pct}}` and the verifier can trace that number back to the two queries it came from.

Planneragent/

The loop that wires the tools together, with step and token budgets. Reuses manual_loop rather than implementing a second agent loop.

src/agent/agent/modes.py218 lines

What shape of answer a task wants, and how to check it.

One agent, one loop, one gateway, two output contracts:

PROSE a warehouse question. The answer is sentences, and every number in them is a {{evidence_id.field}} placeholder. Verified by verifier/check.py: numbers backed, placeholders resolve, parts reconcile with the whole.

Verificationverifier/

Every number traced to evidence, and the parts reconciled against the whole.

src/agent/verifier/check.py169 lines

Does every number in this report come from evidence, and does it add up?

Two different failures, two different checks:

UNBACKED NUMBER -- the model typed a digit instead of a placeholder. Caught by scanning the TEMPLATE, before rendering. After rendering every number looks identical, so a verifier that runs on the output can never tell a cited figure from an invented one. This is the check that has to run early.

Renderingreport/

Turns {{e7.delta_pct}} into a figure. The only thing that converts an id into a digit.

src/agent/report/render.py71 lines

Render {{evidence_id.field}} placeholders from the evidence store.

The model writes prose containing `{{e7.delta_pct}}`. It never writes the digit. This module is the only thing that turns an id into a number, which is what makes "no digit in the report came from model text" a checkable property rather than an intention.

An unresolvable placeholder is an error, not an empty string. Rendering `{{e9.delta}}` as "" would produce a sentence that reads fine and says nothing true -- the worst available failure.

Auditaudit/

Append-only log of every prompt and tool call, including the refusals that leave no evidence behind.

src/agent/audit/log.py138 lines

Append-only JSONL log of everything an agent did, with timings.

Separate from the evidence store on purpose. Evidence answers "where did this number come from"; the audit log answers "what did the system do", including the things that produced no evidence at all -- refused SQL, failed tools, the exact prompt text.

## The schema

The loopmanual_loop/

One request, the tools it asked for, repeat. Written by hand twice -- once per provider -- so the shape of each API stays visible.

manual_loop/cost.py66 lines

Turn token counts into dollars, when the prices are configured.

Deliberately not shipping hardcoded prices. A stale rate in the source is worse than no rate: it reports a confident number that is quietly wrong, and nobody re-checks a figure that already looks plausible.

Set them in .env, from the provider's own pricing page:

manual_loop/loop.py168 lines

Phase 1 — the hand-written Claude tool-use loop.

The loop, and nothing else. It knows how to talk to the Messages API, execute whichever tools it is handed, and stop. It knows nothing about Spider, SQLite, or evaluation -- that belongs to the caller.

Built on the low-level `anthropic` SDK rather than claude-agent-sdk, because a benchmark needs a harness that is fixed, fully owned, and free of the Claude Code CLI's ~19k tokens of system prompt and its built-in tools.

manual_loop/loop_openai.py189 lines

The same hand-written loop, against Luna's Responses API.

`loop.py` talks to Anthropic's Messages API; this talks to OpenAI's Responses API. They return the identical `Result`, so `evals/runner.py` and the orchestrator do not know or care which one ran.

Why a second file rather than a provider flag inside the first: the two APIs disagree about almost everything that matters here -- content blocks vs output items, `stop_reason` vs the absence of one, nested vs flat tool schemas. A single function with branches on every line teaches the shape of neither.

Benchmarkevals/

Spider 2.0-Lite and the gold warehouse set, both run through the same agent.

evals/_run_scorer.py54 lines

Run Spider's evaluate.py unmodified, with the cloud backends stubbed out.

evaluate.py imports `google.cloud.bigquery` at module scope even when scoring local SQLite tasks in exec_result mode, which is the only mode used here. The choices were:

- install google-cloud-bigquery: ~150 MB and a credentials file, for an import that is never called on a `local*` task - edit evaluate.py: it is the one thing in this project deliberately NOT written or modified here, because a scorer you adjust is a scorer you can talk yourself into

evals/run_evals.py235 lines

Score the data agent: execution accuracy, pass^k, confidently-wrong rate.

Three numbers, because one is not enough to make a decision with:

EXECUTION ACCURACY -- fraction of runs that got the right answer. The headline.

evals/run_triage.py57 lines

Run one triage pass over the recorded failures and write the proposals.

uv run python evals/run_triage.py uv run python evals/run_triage.py --quiet

evals/runner.py214 lines

Run the data agent over Spider 2.0-Lite's 135 local (SQLite) tasks.

One agent. This used to be a second one: its own loop, its own single-tool sandbox, its own prompt, and no evidence store -- a parallel stack that shared nothing with the warehouse agent but the HTTP call. Spider tasks now go through the same Planner, the same gateway, and the same deterministic verifier, in `sql` mode rather than `prose` mode.

What that buys beyond less code: the `sql_was_executed` check. A model that explores with five queries and then writes a sixth, clean, never-run one in its final answer used to have that answer scored as if it were tested. Now it is rejected before it reaches the scorer.

evals/score.py190 lines

Score a sweep with Spider's own evaluator, and write the number down.

The agent produces `runs/<sweep>/<task>/result.csv`. Spider's evaluate.py wants a flat directory of `<instance_id>.csv`. This stages one into the other, runs their scorer unmodified, and records the result.

Their scorer, not ours, deliberately. A home-grown comparison that is slightly too lenient invents improvements that never happened -- and in this project six separate measurement bugs have already produced numbers that were simply wrong. The one thing worth not writing ourselves is the thing that decides whether we are right.

evals/score_anomalies.py124 lines

Ask one open question against the seeded warehouse; score what it found.

Different from run_evals.py on purpose. Gold questions measure whether the agent can compute what it was told to compute. This measures whether it would notice something nobody pointed at -- which is the actual job.

Scoring is strict: an anomaly counts as found only when the answer names its month AND at least one keyword describing its cause. "August was weak" is not finding a regional cancellation spike; it is noticing the hole it left.

evals/show_run.py129 lines

Read an audit log back as something a person can scan.

JSONL is the right storage format and the wrong reading format. This renders a run as one line per event, with the timings on the left, so the question "where did the time go" is answerable at a glance rather than by writing a one-off script every time.

uv run python evals/show_run.py runs/spider-budget/local021 uv run python evals/show_run.py runs/spider-budget # whole sweep uv run python evals/show_run.py runs/spider-budget --slow # slowest calls

Improvementorchestrator/

Failure collection, the triage analyst that proposes fixes, and the verdict ledger that records whether a repair landed.

orchestrator/failures.py103 lines

Collect every failure across every run, grouped by signature.

Separated from docs/build_failures.py because two things need this: the HTML report a human reads, and the triage agent that proposes fixes. A collector living inside a renderer can only ever serve the renderer.

orchestrator/findings.py159 lines

Findings that can be checked mechanically, and the ledger that tracks them.

The failure this file exists to prevent: a verifier reports a defect, the worker runs again, and something -- the worker, the verifier, or the orchestrator -- declares it fixed because the second run *said* so. Nothing re-checked it. The loop reports progress it never made.

So a FAIL finding is not prose. It carries a query and the result that query must produce once the defect is gone. Whether feedback landed is then decided by running that query, not by asking a model.

orchestrator/trace.py87 lines

A console view of what the agents are doing, while they do it.

Transcripts on disk answer "what happened". They do not answer "what is it doing right now", and a fifteen-turn loop that prints nothing for two minutes is indistinguishable from one that has hung.

The tracer is a plain callable passed into the loops. Passing nothing keeps them silent, so this file changes no behaviour -- it only makes it visible.

orchestrator/triage.py357 lines

The triage sub-agent: reads failures, proposes fixes, changes nothing.

It is handed grouped failure signatures across every run -- not one transcript -- because the useful question is "which error keeps happening", and a single run cannot answer it.
